# Техническое задание и учебный план: «Совместный плейлист» на Go

**Статус:** согласовано по результатам 35 вопросов.  
**Основа:** предоставленное «Задание 7. Совместный плейлист».  
**Цель:** реализовать HTTP-сервер общей очереди воспроизведения, где конкурентные изменения корректны и детерминированы. Аудиофайлы не загружаются и не воспроизводятся.

> **Приоритет:** корректность состояния и воспроизводимые проверки важнее скорости и количества библиотек. Этот документ отделяет согласованные требования от уточнений реализации, необходимых для однозначного тестирования.

## 1. Объём и ограничения

- Один общий плейлист для всех пользователей, без нескольких комнат или плейлистов.
- Backend на Go со стандартным `net/http`; фронтенд не разрабатывается.
- PostgreSQL — постоянное хранилище и источник истины. Перезапуск Go не сбрасывает пользователей, голоса, историю и текущий трек.
- Пользователи создаются через `POST /users`, без аутентификации. Клиенты передают `userId`; подмена ID технически возможна и считается допустимым учебным ограничением.
- Любой клиент вправе вызвать `play` и `next`. Удалить поставленный в очередь трек вправе только его автор по переданному `userId`.
- Одна инстанция Go-сервера. Гарантии изменений обеспечиваются транзакциями БД (а не только `sync.Mutex`), но межсерверную рассылку SSE не реализуем.
- Нет стриминга аудио, определения длительности треков, автоматического переключения, OAuth/JWT, Spotify/YouTube-интеграций, Kafka, Redis, Kubernetes.

## 2. Стек и принятые решения

| Область | Решение |
|---|---|
| HTTP | Go `net/http`, стандартный `ServeMux` |
| Слои | `handler` → `service` → `repository`, модели `domain` |
| SQL | явные запросы через `pgx/v5`, соединения через `pgxpool` |
| БД | PostgreSQL, `BIGINT GENERATED ALWAYS AS IDENTITY` |
| Миграции | `golang-migrate`, парные `.up.sql`/`.down.sql` |
| Версия | `playback_version`, изменяется только успешными `play`/`next`, которые изменяют воспроизведение |
| Синхронизация | общая строка `playlist_state`, `SELECT ... FOR UPDATE` |
| Голоса | хранить в `votes`; `score = SUM(value)` без кэша |
| Обновления | SSE: только уведомления; состояние запрашивается через REST |
| Логи | стандартный `log/slog`, JSON, `request_id` |
| Настройки | `.env` и системные переменные с приоритетом системных |
| Локальный запуск | Go локально, PostgreSQL в Docker Compose |
| Автотесты | только интеграционные, `testing`, Testcontainers PostgreSQL |
| Нагрузка | отдельная CLI на Go, Worker Pool, подготовка данных через REST |
| Документация | `docs/openapi.yaml` (OpenAPI 3.1), Swagger UI на `/docs/` для разработки |

## 3. Логическая архитектура

```text
HTTP clients / Swagger / loadtest
            |
     net/http ServeMux
            |
  middleware (request_id, logging)
            |
        handlers  <---------- SSE /playlist/events
            |                          ^
         services -------> EventHub (in memory, one instance)
            |
       repositories
            |
       pgxpool / SQL
            |
        PostgreSQL
```

- **Handler:** JSON-декодирование, проверка формата, маршрутные параметры, mapping ошибок в HTTP.
- **Service:** бизнес-правила, orchestration операций и гарантия транзакционных границ.
- **Repository:** SQL и доступ к БД; не решает, кто имеет право удалить трек.
- **Domain:** типы (`User`, `PlaylistItem`, `Vote`, `PlaylistState`), статусы и бизнес-ошибки.
- **EventHub:** подписки и публикация уведомлений после `COMMIT`. Доставка best effort; потеря уведомления не меняет данные.

Не вводить интерфейс для каждого класса/файла автоматически. Интерфейсы добавлять только при реальной необходимости разделить зависимости.

## 4. Модель данных PostgreSQL

### 4.1. `users`

| Поле | Тип | Правило |
|---|---|---|
| `id` | `BIGINT` | `GENERATED ALWAYS AS IDENTITY PRIMARY KEY` |
| `name` | `TEXT` | `NOT NULL`, непустое после обрезки краевых пробелов |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` (удобное дополнение) |

### 4.2. `playlist_items`

| Поле | Тип | Правило |
|---|---|---|
| `id` | `BIGINT` | `IDENTITY PRIMARY KEY` |
| `title` | `TEXT` | `NOT NULL`, непустое |
| `artist` | `TEXT` | `NOT NULL`, непустое |
| `url` | `TEXT` | `NULL`, необязательно, формат не проверяем |
| `added_by` | `BIGINT` | `NOT NULL REFERENCES users(id)` |
| `status` | `TEXT` | `queued`, `playing`, `played`, `removed` |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` |
| `started_at` | `TIMESTAMPTZ` | `NULL` до первого `play` |
| `played_at` | `TIMESTAMPTZ` | `NULL` до завершения |

Рекомендуется `CHECK (status IN (...))` и частичный уникальный индекс:

```sql
CREATE UNIQUE INDEX one_playing_item
  ON playlist_items ((true)) WHERE status = 'playing';
```

Это **дополнительная защита на уровне БД** от двух одновременно играющих треков. Для одного плейлиста индекс подходит.

### 4.3. `votes`

| Поле | Тип | Правило |
|---|---|---|
| `id` | `BIGINT` | `IDENTITY PRIMARY KEY` |
| `item_id` | `BIGINT` | `NOT NULL REFERENCES playlist_items(id)` |
| `user_id` | `BIGINT` | `NOT NULL REFERENCES users(id)` |
| `value` | `SMALLINT` | `NOT NULL CHECK (value IN (-1,1))` |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` |
| `updated_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` |

Обязательно `UNIQUE (item_id, user_id)`. Повторная оценка с тем же значением — no-op; изменение выполняется через `INSERT ... ON CONFLICT (...) DO UPDATE`. При удалении голоса запись из `votes` удаляем физически — это согласовано с отсутствием отдельного журнала событий.

### 4.4. `playlist_state`

Одна служебная запись:

```text
id = 1
playback_version = 1
```

`id` — фиксированный числовой ключ (не `IDENTITY`). Должно быть ограничение `CHECK (id = 1)` и первичный ключ. Начальная запись создаётся миграцией. Текущий `playing` определяется по статусу в `playlist_items`, а не дублируется в этом состоянии.

### 4.5. Индексы

- Уникальный `votes(item_id, user_id)` — защита от повторных голосов и ускорение поиска.
- `playlist_items(status, created_at, id)` — отбор ожидающих элементов и упорядочивание при равных рейтингах; окончательный порядок по рейтингу всё равно требует агрегирования.
- `playlist_items(status, played_at DESC)` — история.
- Частичный уникальный индекс `one_playing_item` — гарантия максимум одного `playing`.

Измерить планы запросов `EXPLAIN (ANALYZE, BUFFERS)` при нагрузочном исследовании; не обещать, что индекс полностью устранит вычисление `SUM(votes.value)`.

## 5. Жизненный цикл и бизнес-правила

```text
queued --> playing --> played
   |
   +------> removed
```

- `queued`: участвует в очереди и голосовании.
- `playing`: максимум один, не участвует в сортировке и голосовании.
- `played`: сохраняется в истории; нельзя снова запустить.
- `removed`: логически удалён; не участвует в очереди и голосовании.
- Удалять разрешено **только `queued` и только добавившему пользователю** (проверка `added_by == userId`).
- Сервер устанавливает ID, статус и временные метки, клиент не управляет `score`.

### 5.1. Голосование

- Только `queued`; значения только `-1` и `+1`.
- Для `(item_id, user_id)` максимум одна активная запись.
- Повторный одинаковый голос ничего не меняет, не создаёт вторую запись и не вызывает `vote_changed`.
- Смена `+1 -> -1` изменяет суммарный рейтинг на `-2`, и наоборот на `+2`.
- `DELETE` убирает свой голос. Повторный `DELETE` отсутствующего голоса считать успешным no-op (зафиксированное уточнение реализации).
- `score` всегда вычисляется по сохранённым голосам; отсутствие голосов означает `0`.

### 5.2. Порядок очереди

Только `queued`, сортировка **строго** по:

```text
score DESC, created_at ASC, id ASC
```

`playing` показывается отдельно и не переставляется после новых голосов.

### 5.3. `play` и `next`

- `play`: если ничего не играет и в очереди есть элементы, выбирает лучшего `queued`, переводит в `playing`, пишет `started_at`, увеличивает `playback_version`. Если `playing` уже есть — `409 ALREADY_PLAYING`; если очередь пуста — `409 PLAYLIST_EMPTY` (уточнение реализации).
- `next`: клиент присылает `expectedVersion`; если не совпадает — `409 VERSION_CONFLICT` без изменений. Если текущего `playing` нет — `409 NOTHING_PLAYING`.
- Если текущий трек существует: перевести в `played`, выставить `played_at`, выбрать лучшего `queued`, перевести его в `playing` и выставить `started_at`. Если очереди нет — `playing = null`. Затем увеличить `playback_version` на 1.
- `play` также принимает `expectedVersion`, чтобы клиент не запускал воспроизведение по устаревшему состоянию (уточнение интерфейса, согласующееся с ранее выбранным версионированием).
- Ошибочные запросы, no-op и изменение голосов/добавление/удаление треков **не увеличивают** `playback_version`.

## 6. Конкурентность и транзакции

### 6.1. Правило сериализации

Для **каждой операции изменения плейлиста** (`add`, `vote`, `delete vote`, `remove`, `play`, `next`):

```sql
BEGIN;
SELECT playback_version FROM playlist_state WHERE id = 1 FOR UPDATE;
-- проверки и чтение текущего состояния
-- модификации
COMMIT;
```

В реализации транзакции используй `pgx.BeginTx(ctx, ...)` и `defer tx.Rollback(ctx)` как защиту; явный `Commit(ctx)` после всех проверок. `ROLLBACK` после успешного commit безопасно игнорируется как уже завершённая транзакция.

**Почему блокируется и `vote`:** чтобы `next` не выбирал победителя на данных, которые меняются посреди выбора; при этом голоса не увеличивают `playback_version`. Порядок операций определяется порядком захвата общей блокировки и успешным commit.

### 6.2. Атомарный `next`

1. Начать транзакцию и заблокировать `playlist_state`.
2. Проверить `expectedVersion` после получения блокировки.
3. Найти текущий `playing`; при отсутствии вернуть бизнес-ошибку.
4. Завершить текущий (`played`, `played_at`).
5. Вычислить рейтинг queued-элементов в БД, выбрать максимум по `score DESC, created_at ASC, id ASC`.
6. При наличии следующего сделать `playing`, `started_at`.
7. Обновить `playback_version = playback_version + 1`.
8. `COMMIT`; только после него отправить SSE-уведомление.

Два одновременных `next` с одинаковым `expectedVersion` не пропустят два трека: один проходит, второй после ожидания блокировки получает `409`.

### 6.3. Проверяемые гонки

| Сценарий | Ожидаемое свойство |
|---|---|
| 100 разных пользователей ставят `+1` | Ровно 100 голосов, `score = 100` |
| 20 одновременных `+1` от одного пользователя | Одна запись, `score = 1` |
| `vote` одновременно с `next` | Следующий соответствует одному корректному последовательному порядку транзакций |
| `add` одновременно с `next` | Детерминированный итог в зависимости от порядка блокировки |
| `remove` одновременно с `next` | Удалённый элемент не может одновременно стать `playing` |
| Два `next` с одной версией | Одна смена, второй `409 VERSION_CONFLICT` |
| Любые операции | Не более одного `playing` |

**Компромисс:** общая строка создаёт hotspot; операции сериализуются и могут увеличивать latency. Это сознательный выбор простоты и корректности для одного плейлиста.

## 7. REST API

Все JSON-тела и ответы оформляются в `camelCase`; ID — целые числа JSON, в Go — `int64`. Варианты ответов и статус-коды ниже обязательны для реализации после закрепления OpenAPI.

| Метод | Маршрут | Назначение |
|---|---|---|
| `POST` | `/users` | Создание пользователя |
| `GET` | `/playlist` | `playing`, упорядоченная `queue`, `playbackVersion` |
| `POST` | `/playlist/items` | Добавить трек |
| `POST` | `/playlist/items/{id}/vote` | Создать/обновить голос |
| `DELETE` | `/playlist/items/{id}/vote?userId=1` | Отменить свой голос |
| `DELETE` | `/playlist/items/{id}` | Логически удалить queued-трек; тело `{"userId":1}` |
| `POST` | `/playlist/play` | Начать воспроизведение |
| `POST` | `/playlist/next` | Завершить текущий и выбрать следующий |
| `GET` | `/playlist/history` | Завершённые треки, новые в начале |
| `GET` | `/playlist/events` | SSE-подписка |
| `GET` | `/docs/` | Swagger UI для локальной разработки |

### 7.1. Примеры

`POST /users`:

```json
{"name":"Max"}
```

Ответ `201 Created`: `{"id":1,"name":"Max"}`.

`POST /playlist/items`:

```json
{"userId":1,"title":"The Pot","artist":"Tool","url":"https://example.com/song"}
```

`201 Created`: объект трека с `id`, `status: "queued"`, `score: 0`, `createdAt`.

`POST /playlist/items/10/vote`:

```json
{"userId":1,"value":1}
```

`200 OK`: `{"itemId":10,"userId":1,"value":1,"score":3}`. Если это повтор того же голоса, возвращается то же актуальное состояние без изменения данных.

`GET /playlist`:

```json
{
  "playing": {"id":10,"title":"The Pot","artist":"Tool","status":"playing","score":2},
  "queue": [{"id":12,"title":"Change","artist":"Deftones","status":"queued","score":7}],
  "playbackVersion": 5
}
```

`POST /playlist/next` (аналогично `play`):

```json
{"expectedVersion":5}
```

`200 OK`: `{"playing":null,"playbackVersion":6}` при завершении последнего трека.

`GET /playlist/history` возвращает массив завершённых треков, сортировка `played_at DESC, id DESC`.

### 7.2. Валидация

- Обязательные `title`, `artist`, `name` — непустые после `strings.TrimSpace`.
- `url` — необязательная строка, без проверки формата; `null` или отсутствие поля допускаются.
- `userId`/ID маршрута — положительные числа; пользователь должен существовать.
- `value` — строго `-1` или `1`.
- Невалидный JSON, неверные типы и отсутствующие поля — `400 INVALID_REQUEST`.
- Клиенту запрещено управлять `score`, статусом, ID, временными метками. Нежелательные дополнительные поля JSON целесообразно отклонять через `DisallowUnknownFields` (уточнение реализации).

### 7.3. Ошибки

Единый формат:

```json
{"error":{"code":"VERSION_CONFLICT","message":"Playback state has changed"}}
```

| HTTP | Код | Пример |
|---|---|---|
| 400 | `INVALID_REQUEST` | неверный JSON или пустое обязательное поле |
| 400 | `INVALID_VOTE` | голос не -1/+1 |
| 403 | `ITEM_ACCESS_DENIED` | удаление чужого трека |
| 404 | `USER_NOT_FOUND` | несуществующий `userId` |
| 404 | `ITEM_NOT_FOUND` | несуществующий трек |
| 409 | `ITEM_NOT_QUEUED` | голосование за `played` или `removed` |
| 409 | `VERSION_CONFLICT` | устаревший `expectedVersion` |
| 409 | `ALREADY_PLAYING` | `play` при текущем playing |
| 409 | `NOTHING_PLAYING` | `next` без playing |
| 409 | `PLAYLIST_EMPTY` | `play` без queued |
| 500 | `INTERNAL_ERROR` | неожиданная техническая ошибка |

Бизнес-ошибки преобразуются в HTTP в handler. Ошибки БД логируются технически, наружу отдаётся безопасное общее сообщение.

## 8. SSE

`GET /playlist/events` — заголовок `Content-Type: text/event-stream`.

События: `item_added`, `item_removed`, `vote_changed`, `playback_changed`.

```text
event: vote_changed
data: {"itemId":15}

```

- Публикация только **после успешного commit**; повторный одинаковый голос/отсутствующие изменения событий не генерируют.
- Уведомления best effort, не хранятся в БД; отсутствие гарантированной доставки — заявленное ограничение.
- Не отправлять весь плейлист в событии; клиент запрашивает `GET /playlist`.
- При открытии/переподключении клиент читает полный снимок через REST; SSE может потерять событие между подпиской и чтением — для устойчивого клиента рекомендуется сначала открыть SSE, затем прочитать REST и при уведомлениях повторять чтение.
- EventHub не должен бесконечно блокировать REST-обработчик на медленном подписчике: ограниченный буфер, неблокирующая публикация, политика отключения медленного клиента.
- При разрыве соединения отменить подписку через `r.Context()` и освободить ресурсы.
- Для SSE не использовать обычный 5-секундный тайм-аут запроса. Поддержать flush после события и heartbeat-комментарии для активного соединения.
- Рассылка между инстанциями не входит в MVP.

## 9. Конфигурация, HTTP и остановка

`.env` читается через `godotenv` локально, реальные переменные окружения важнее файла; `.env` в `.gitignore`, `.env.example` публикуется без реальных секретов. Пример:

```dotenv
SERVER_PORT=8080
DATABASE_URL=postgres://playlist:playlist@localhost:5432/playlist?sslmode=disable
LOG_LEVEL=info
DB_MAX_CONNECTIONS=10
HTTP_TIMEOUT=5s
DB_OPERATION_TIMEOUT=3s
DB_CONNECT_TIMEOUT=10s
SHUTDOWN_TIMEOUT=10s
```

- `pgxpool` создаётся при старте, проверяется подключение (`Ping`) с 10-секундным deadline.
- `ctx` передаётся по `handler -> service -> repository`. Транзакция и SQL укладываются в 3 секунды; обычный HTTP-запрос имеет предельное время 5 секунд. Проверить, чтобы тайм-ауты HTTP-сервера не обрывали SSE (в частности `WriteTimeout`), и правильно настроить `ReadHeaderTimeout`.
- JSON-логи через `log/slog`: метод, маршрут, статус, длительность, `request_id`; исключать секреты.
- Остановка по `SIGINT`/`SIGTERM`: прекратить принимать новые подключения, закрыть SSE-подписки, вызвать `http.Server.Shutdown` с лимитом 10 секунд, затем закрыть `pgxpool`. Длительные SSE подключениями управляет EventHub, не полагаться только на `Shutdown`.
- Сбой миграции/БД при старте — понятная ошибка, сервер не должен объявлять готовность без БД.

## 11. Интеграционное тестирование

**Только интеграционные тесты** на реальной PostgreSQL через `testcontainers-go` и стандартный `testing`; не требуется отдельный слой unit-тестов. В тестах можно вызывать и HTTP API через `httptest`, и реальные репозитории в тестовом окружении. Схема применяется миграциями. Docker должен быть доступен.

Обязательная матрица:

1. Создание пользователя; неверные данные и неизвестный пользователь.
2. Добавление трека и чтение очереди.
3. Сортировка по `score DESC, created_at ASC, id ASC`, включая ties.
4. Голос `+1`, `-1`, смена значения, повторный голос и отмена.
5. 100 конкурентных голосов разных пользователей: `score == 100`.
6. 20 конкурентных одинаковых голосов одного пользователя: одна запись, `score == 1`.
7. `play` успешен, повторный `play` запрещён, очередь пуста.
8. `next` запускает лучшего; последний `next` завершает playing; `next` без playing возвращает 409.
9. Два конкурентных `next` с одинаковой версией: один успешен, второй 409, без пропуска.
10. `vote vs next`, `add vs next`, `remove vs next`: допустимая последовательность и максимум один playing.
11. Удаление queued только автором, отказ для played/playing.
12. История и сохранность состояния после остановки и перезапуска экземпляра приложения с той же БД.
13. SSE-уведомление после commit, отключение подписчика, отсутствие события при rollback/no-op.
14. Graceful shutdown, закрытие SSE, context cancellation и тайм-ауты.
15. `go test ./...` и `go test -race ./...` проходят.

В конкурентных тестах использовать общий стартовый барьер, например канал, и `sync.WaitGroup`; не рассчитывать, что быстро запущенные goroutines обязательно пересекутся по времени. Тесты должны быть повторяемыми и независимыми.

## 12. Нагрузочная CLI

`cmd/loadtest`: отдельная программа на Go, используем `http.Client`, Worker Pool (фиксированное число workers, задания по каналу), сбор результатов через канал, общий клиент с повторным использованием соединений.

Пример:

```bash
go run ./cmd/loadtest -scenario=vote -workers=100 -requests=10000 -base-url=http://localhost:8080
```

**Два этапа:** `prepare` (создание тестовых пользователей, треков и голосов **только через REST API**) и `run` (измеряемая нагрузка). Не смешивать время подготовки с метриками измерения.

Метрики: общее число запросов, успехи/ошибки по статусам, RPS, среднее время, p50/p95/p99. Для сценариев `next` 409 — ожидаемый результат конкурентной защиты, учитывать отдельно от технических ошибок.

Профили:
- 1000 queued items, 100 users, 10 000 votes.
- 100 параллельных голосов.
- 1000 пользователей за один hot item: для этого профиля **дополнительно создаются 1000 пользователей**, поскольку 100 пользователей не могут дать 1000 уникальных активных голосов за один трек.
- `GET /playlist`, `vote`, `next`, смешанные операции и размер/время рассылки SSE по возможности.

Для каждого прогона записывать окружение, число соединений в пуле, workers, RPS, latency, ошибки и выводы. Повторить запуски и сравнить результаты. Не заявлять заранее целевые миллисекунды — требования источника предусматривают **измерение**, а не конкретный SLA.

## 14. Приёмочные критерии

- [ ] Можно создать пользователя и добавить несколько треков.
- [ ] Клиенты видят один плейлист, текущий трек и очередь в правильном порядке.
- [ ] Голоса только ±1, один пользователь — один голос на трек, можно изменить и отменить.
- [ ] Порядок изменяется при голосах; tie-break всегда детерминирован.
- [ ] Не более одного playing даже под конкурентной нагрузкой.
- [ ] `play` и `next` атомарны, с контролем `playback_version`.
- [ ] Конкурентный `next` не приводит к двойному пропуску.
- [ ] 100 параллельных уникальных голосов сохраняются полностью.
- [ ] Повторные голоса одного пользователя не увеличивают рейтинг многократно.
- [ ] `vote vs next`, `add vs next`, `remove vs next` дают согласованный результат.
- [ ] Удаление queued доступно только автору, запись остаётся для истории.
- [ ] История played доступна через API, данные сохраняются после restart.
- [ ] SSE уведомляет подписчиков; отключения и медленные клиенты обработаны.
- [ ] Контексты и timeout используются в HTTP и SQL, graceful shutdown реализован.
- [ ] `go test ./...` и `go test -race ./...` проходят.
- [ ] Нагрузочный инструмент выдаёт метрики и результаты экспериментов.

## 16. Принятые уточнения без дополнительных вопросов

Чтобы спецификация была реализуемой и проверяемой, здесь перечислены конкретизации, **которые не были отдельными вопросами**. Они не меняют основные согласованные решения:

1. `play` принимает `expectedVersion`, как и `next`; `PLAYLIST_EMPTY` — конфликт для `play` при пустой очереди.
2. `DELETE /vote` принимает `userId` как query parameter; `DELETE /items/{id}` — в JSON-теле.
3. Повторный DELETE отсутствующего голоса — успех без изменений.
4. Добавлены `created_at` для пользователей и `updated_at` для голосов, а также полезные SQL CHECK и индексы.
5. Для SSE выбран ограниченный буфер и отключение медленного подписчика вместо бесконечной блокировки.
6. Для облегчения документации и тестирования предложены конкретные JSON-формы успешных ответов, которые не были отдельно утверждены пользователем.
7. `GET /playlist/history` сортируется по времени завершения, затем по ID.

Если эти детали станут принципиальными при реализации, их можно изменить отдельно, сохранив согласованную бизнес-логику.
